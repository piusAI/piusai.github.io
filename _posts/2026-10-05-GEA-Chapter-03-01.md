| |Interface|Mix-in|
|---|---|---|

|상태|없음|가질 수는 있지만 작게 유지|


> 💡 **인터페이스끼리의 상속**도 가능하다. 약속을 단계적으로 확장할 때 쓰지만, 보통은 작은 인터페이스를 다중상속으로 조합하는 쪽을 선호한다. 인터페이스 두 개가 같은 상위 인터페이스를 상속하면 다이아몬드가 생기는데, 이때는 `virtual` 상속을 쓴다.
``` cpp

```



- 다형성 | Polymorphism
  가상함수로 설정해, 구체적인 정보는 객체/자식 들의 나머지 코드로 분리.

- 합성 vs 집합 (GEA 책 용어)
	- 합성(Composition) : Has-a 관계 
	- 집합(Aggregation) : Uses-a 관계

```cpp
class Engine{public : void start(){}};
class Station;

class Car{
	Engine engine_;                          // 1) 합성 : 값으로 직접 포함(합성)
	std::unique_ptr<Engine> engine2_;        // 2) 합성(Pointer로 소유)
	Engine* engine_3;                         // 3) 집합 : Pointer로 참조만(소유 x)
public:
	Car(Engine* e) : engine_3(e){}
	
	void refuel(Station& station){           // 집합 (use-a, 잠깐 사용)
		station.supply(*this);               // 매개 변수로 받아서 쓰고 끝
	}
};

```

> 💡 **UML 기준과 비교** (책의 용어는 실무적으로 느슨해서 UML과 다르다. 면접/시험에서는 UML 기준으로 답하는 게 안전하다.)

| 코드 모양                              | UML                     | GEA 책       |
| ---------------------------------- | ----------------------- | ----------- |
| `Engine e_;`, `unique_ptr<Engine>` | 합성 (소유하는 has-a)         | 합성 (has-a)  |
| `Engine* e_;` (멤버)                 | 집합 (소유 안 하는 has-a)      | 집합 (uses-a) |
| 매개변수 / 지역 변수                       | 의존 (dependency, uses-a) | 집합 (uses-a) |

>두 체계 모두 공통 기준은 **"소유하면 합성, 소유 안 하면 집합(또는 uses-a)"** 이다. UML 표기: 합성 = 채운 마름모, 집합 = 빈 마름모, 의존 = 점선 화살표.

- **Abstract Factory** :
  >서로 연관된 객체들의 set를 만드는 interface제공, 어떤 구체 클래스 만들지는 팩토리 구현체가 결정
``` cpp
#include <iostream>
#include <memory>

// ---------- 제품 인터페이스 ----------
class IButton {
public:
    virtual void draw() = 0;
    virtual ~IButton() = default;
};

class ICheckBox {
public:
    virtual void draw() = 0;
    virtual ~ICheckBox() = default;
};

// ---------- 구체 제품: Windows 계열 ----------
class WinButton : public IButton {
public:
    void draw() override { std::cout << "Windows 버튼\n"; }
};
class WinCheckBox : public ICheckBox {
public:
    void draw() override { std::cout << "Windows 체크박스\n"; }
};

// ---------- 구체 제품: Mac 계열 ----------
class MacButton : public IButton {
public:
    void draw() override { std::cout << "Mac 버튼\n"; }
};
class MacCheckBox : public ICheckBox {
public:
    void draw() override { std::cout << "Mac 체크박스\n"; }
};

// ---------- 추상 팩토리 ----------
class IGuiFactory {
public:
    virtual std::unique_ptr<IButton>   createButton()   = 0;
    virtual std::unique_ptr<ICheckBox> createCheckBox() = 0;
    virtual ~IGuiFactory() = default;
};

// ---------- 구체 팩토리 ----------
class WinFactory : public IGuiFactory {
public:
    std::unique_ptr<IButton>   createButton()   override { return std::make_unique<WinButton>(); }
    std::unique_ptr<ICheckBox> createCheckBox() override { return std::make_unique<WinCheckBox>(); }
};

class MacFactory : public IGuiFactory {
public:
    std::unique_ptr<IButton>   createButton()   override { return std::make_unique<MacButton>(); }
    std::unique_ptr<ICheckBox> createCheckBox() override { return std::make_unique<MacCheckBox>(); }
};

// ---------- 클라이언트: 구체 클래스를 전혀 모름 ----------
void buildUI(IGuiFactory& factory) {
    auto button   = factory.createButton();
    auto checkBox = factory.createCheckBox();
    button->draw();
    checkBox->draw();
}

int main() {
    WinFactory win;
    MacFactory mac;

    buildUI(win);   // Windows 버튼, Windows 체크박스
    buildUI(mac);   // Mac 버튼, Mac 체크박스
}
```


| 역할     | 클래스                        | 설명                                             |
| ------ | -------------------------- | ---------------------------------------------- |
| 추상 팩토리 | `IGuiFactory`              | 관련된 제품 **여러 개(세트)**를 만드는 약속 (순수 가상)            |
| 구체 팩토리 | `WinFactory`, `MacFactory` | 어떤 구체를 `new`(생성)할지 **고르기만** 한다. 그려지는 실제 로직은 없음 |
| 구체 제품  | `WinButton` 등              | **실제 구현**                                      |
| 클라이언트  | `buildUI`                  | 인터페이스만 알고 구체 클래스는 전혀 모름                        |


> 💡 **장단점**
> 	👉🏻 같은 팩토리는 같은 계열 제품만 만들므로 Windows 버튼 + Mac 체크박스가 섞이지 않는다.
> 	👉🏻 새 계열(Linux) 추가: 제품 + 팩토리만 추가하면 된다. `buildUI`는 수정 불필요.
> 	👉🏻 새 제품 종류(ScrollBar) 추가: **모든 팩토리를 수정**해야 한다. (단점)
> 	👉🏻 Factory Method는 제품 **하나**를 만드는 메서드를 서브클래스가 오버라이드하는 것, Abstract Factory는 제품 **세트**를 만드는 객체다.
> 	👉🏻 게임 엔진 예: DirectX / OpenGL / Vulkan별로 텍스처, 버퍼, 셰이더 세트를 만드는 구조.



- **RAII**( Resource Acquision is Initialization):
	- 획득과 동시에 초기화하는 패턴!
	- 리소스의 획득과 반환이 각각의 생성자/파괴자에 묶이는 것을 의미 : 자원 반환 잊는 일을 방지
  
``` cpp
class AllocJanitor
{
public:
	AllocJanitor(mem::Context ctx)
    {
    	mem::PushContext(ctx);
   	}
    ~AllocJanitor()
    {
    	mem::PopContext();
    }
};

void f()
{
    { //scope를 인위적으로 만듦
        AllocJanitor Janitor(mem::Context::kSingleFrame);

        U8* pByteBuffer   = new U8[SIZE];
        float* pFloatBuffer = new float[SIZE];
    } //scope 벗어나면 ~AllocJanitor()가 호출되어 context 복원
}
```
-  Scope로 인위적으로 나오면 `AllocJanitor` 소멸, 할당 컨텍스트 원래대로 돌림.
- `pByteBuffer`, `pFloatBuffer` 자체는 `delete`되지 않는다.
  그렇지만, SingleFrame 메모리 풀은 **프레임이 끝날때 한번 리셋되는 할당자**이므로, 전부 초기화된다??

##### 03 **POD** : Plain Old Data
- C 스타일 구조체처럼 메모리 복사해도 안전한 타입
- 특별한 생성/소멸/복사 의미가 없는 data Type
``` cpp
struct Vertex
{
	float X;
    float Y;
    float Z;
    int id;
    
};

Vertex v{1.2f, 1.8f, 0.f, 2);
// 01 "사용자 정의 생성자"없고 Memory 레이아웃 단순화 : POD성격
// 02 POD는 생성자를 쓰면 안됨!
```

``` cpp
Vertex - POD
┌─────────┬─────────┬─────────┬─────────┐
│ float x │ float y │ float z │  int id │
└─────────┴─────────┴─────────┴─────────┘
```
- 이처럼 단순하게 데이터가 놓여있다
> POD/ 단순 데이터 구조 → 메모리 레이아웃 단순 → raw byte 복사 가능  → GPU buffer에 데이터 올리기 좋다

- 여기에 쓰는것처럼 POD아닌 타입 초기화에도 적용하는 균일초기화(uniform Initialization)문법

  

##### 04 `explicit` 생성자

암시적 변환을 막는 생성자 키워드
``` cpp
struct Sogi
{
	explicit Sogi(int x): X(x) {}

Sogi a = 10; // ❌ 불가 (explicit이면 암시적 변환 막힘)

```

##### 06 **람다함수 & 클로저(closure)**

``` cpp
int main() {

```

- **Enum을** 활용하여 코드를 분리해서 정확한 원인을 알려주라!
- **Stack unwinding** : 예외 발생 시, 중첩된 함수 호출 스택을 되돌아가며 **이미 생성된 객체들의 소멸자 호출**하는 과정
- **RAII**을 쓰면, 생성이 예외 던지지않고 성공했다는것 : **자원 획득** 성공!

Q) 왜 컴파일러는 함수의 스택을 되돌리는 방법을 미리 알아야 하는가?  
A) LIFO 구조의 stack을 기준으로 생성된 객체의 소멸자를 **정확히 역순**으로 호출하여 리소스, 누수, 데드락 상태 붕괴를 막기 위해!  

- Stack Unwinding자체는 구현하지 않는다! (컴파일러의 일)

그렇다면 내가 해야 할 것은?  
1. 리소스는 반드시 스택객체(RAII)로 감싼다
2. 소멸자는 절대 thorw 하지 않도록 해라(C++ 이후 소멸자 기본 `noexcept`)  
소멸자에 정리 코드만 있다면 Resource는 자동으로 안전히 정리된다!
``` cpp
void FOO(){
	auto f = std::make_unique<File>("data.txt");
	//예외 나도 스코프 벗어나서 File 소멸자 호출
}

//절대 하 지 말 라 고!
struct Bad{
	~Bad() noexcept(false) {throw std::runtime_error("no!");}
}

```

  >💡 예외 처리를 쓰면 unwinding 관련 코드가 늘어나 **코드 크기가 커지고 I-cache 성능이 떨어질 수 있다.** 그래서 게임 엔진은 예외 대신 assert 중심으로 가는 경우가 많다.

**언리얼** 방식 - check Macro:
``` cpp
check Macro

void UMyClass::Dosth()
{
	check(PlayerController != nullptr);
    checkf(Health >0, TEXT("Health must be positive"));
}
```


|매크로|동작|
|---|---|
|`check()`|조건 실패 시 **즉시 크래시**|
|`checkf()`|`check` + 메시지 출력|
|`verify()`|표현식은 항상 실행, **실패 검사는 Debug/Development 빌드에서만**|
|`ensure()`|에러를 **로깅만 하고 실행 계속**|

|접근 방식|예시|
|---|---|
|방어적|`IsValid(PlayerController)`|
|공격적 (크래시 바로)|`check(PlayerController != nullptr)`|
|하이브리드 (개발 중 발견, 릴리스에선 계속 실행)|`ensure(PlayerController != nullptr)`|

> ⚠️ 원본의 `PlayerController->IsValid()`는 포인터가 null이면 null 포인터 호출이라 위험하다. 방어적 체크는 **전역 함수 `IsValid(Ptr)`** 로 쓴다.

#### 3.2.3.3 Assertion
- PGO Build : Profile-Guided Optimization 
- Release - Debug 빌드 다르게 하려고 `ASSERT()`매크로 구현!

##### ASSERT 매크로와 dangling else:
 `ASSERT`를 단순한 `if`문으로 만들면 `else`가 엉뚱한 `if`에 붙는다.

``` cpp
if( Sth_condition )
	ASSERT( pointer != nullptr);
else		// 요 else는 어느 if의 것일까?
	DoRecovery();

// 전처리 이후의 확장
if( Sth_condition )
	if( !(pointer != nullptr) ) abort();
else		// 컴파일러는 이 else를 가장 가까운 if인, ASSERT안이 if에 붙힘!!
	DoRecovery();
```

해결 : 매크로가 **else**까지 딸린 하나의 문장이 되도록 구현!
``` cpp
#ifndef NDEBUG
    #define ASSERT(expr)                                       \
        do {                                                   \
            if (!(expr)) {                                     \
                OnAssertionFailed(#expr, __FILE__, __LINE__);  \
                debugBreak();                                  \
            }                                                  \
        } while (0)
#else
    #define ASSERT(expr)      // Release에서는 아무것도 안 함
#endif
```
- `do{ ... } while(0)`덕에 `ASSERT(x);`가 완전한 문장이 되어 `if/else`사이에 써도 안전
- `#expr`:식을 문자열로 만들어 실패 메시지에 출력

##### 전처리기 Tip
1.  전처리기는 줄 바꿈을 문장 끝으로 생각하니 \를 꼭 써야 한다!
2. `\`뒤에는 아무것도 오면 안됨. 공백, 주석 모두다
``` cpp
#define BAD(expr) \   // ❌ \ 뒤에 주석이 있으면 줄 연결이 깨질 수 있음
    sth();

#define GOOD(expr) \
    sth();            /* 주석은 이렇게 /* */ 로, 그리고 \ 와 같은 줄에 두지 않기 */
```

#### Assertion When Compile - STATIC_ASSERT
- 일반 `ASSERT`는 런다임에 검사하므로 컴파일 타임에는 알수 없음
  -> STATIC_ASSERT  C++11부터 나왔어서 이식성을 위해 그 전 버전은 직접 구현.

##### 방법 01. **0으로 나누기**(오류 심기):

``` cpp
#define _ASSERT_GLUE(a,b) a##b
#define ASSERT_GLUE(a, b) _ASSERT_GLUE(a,b)

#define STATIC_ASSERT(expr)\
	enum\
{\
    ASSERT_GLUE(g_assert_faile_, __LINE__) = 1 / (int)(!!(expr))\
};
```
- `expr`이 거짓이면 `1 / 0`이 되어 **상수식에서 0으로 나누기 → 컴파일 에러**
- `!!(expr)` : 어떤 값이든 0 또는 1로 만든다.
- `g_assert_fail_` + `__LINE__` : 줄 번호를 붙여 enum 이름이 **겹치지 않게** 한다.
- `ASSERT_GLUE`를 **두 단계**로 만드는 이유 : `##`가 붙은 인자는 매크로 확장이 일어나지 않아서, 한 단계만 쓰면 `__LINE__`이 숫자로 바뀌기 전에 이어 붙여진다.

```
//에러 예시
error: division by zero in constant expression
   ASSERT_GLUE(g_assert_faile_, 123) = 1 / (int)(!!(expr))
   ~~~~~^~~~~~~~~~~~~~~~~~~~~~~~~~~~
```


  C+11의 `static_assert`의 사용법:
  
``` cpp
struct FMyNetworkPacket {
    uint32_t Header;       // 4바이트
    char Data[120];        // 120바이트
    uint32_t Footer;       // 4바이트
    // 총합: 4 + 120 + 4 = 128바이트 (패딩 없음)

// 구조체 선언이 끝난 "뒤"에 둔다
    static_assert(sizeof(FMyNetworkPacket) == 128,
                  "FMyNetworkPacket must be exactly 128 bytes for network alignment!");
};
```
> ⚠️ 원본은 `static_assert`를 구조체 **안**에 넣었는데, 구조체 본문 안에서는 아직 클래스가 불완전 타입이라 `sizeof(FMyNetworkPacket)`을 쓸 수 없다. 선언 뒤로 빼야 한다.

##### 방법 02 Template 특수화를 사용한 방법
``` cpp
#ifdef __cplusplus
#if __cplusplus >= 201103L          // C++11 이상인가?
    #define STATIC_ASSERT(expr) \
        static_assert(expr, "static assert failed:" #expr)
#else                              
	// C++98 / C++03 시절
    // static_assert가 없으므로 템플릿 특수화로 구현
    
    template<bool>
    class TStaticAssert;           // 선언만 (정의 없음)
	template<>
	class TStaticAssert<true> {};      // true 특수화 → 빈 클래스 (정의 있음)
    
    #define ASSERT_GLUE2(x, y) x##y
    #define ASSERT_GLUE(x,y) ASSERT_GLUE2(x,y)
    
    #define STATIC_ASSERT(expr) \
    enum \
	{ ASSERT_GLUE(g_assert_fail_, __LINE__) = sizeof(TStaticAssert<!!(expr)>)} 
	#endif
#endif
```
**동작 원리**
- `TStaticAssert`는 **선언은 항상**, **정의는 `true`일 때만** 있다.
- `expr`이 `true` → `TStaticAssert<true>` (정의 있음, `sizeof` = 1) → 통과
- `expr`이 `false` → `TStaticAssert<false>` (정의 없는 **불완전 타입**) → `sizeof`가 불가능 → **컴파일 에러**
- `!!(expr)` : 조건식을 `bool`로 만들어 템플릿 인자에 넣는다.

**템플릿 문법 정리**
- `template<bool>` : 타입이 아닌 **bool 값**이 들어온다 → **비타입 템플릿 매개변수** (`template<bool B>`와 동일, 값을 안 쓰니 이름 생략)
- `template<>` : 이미 있는 템플릿의 **특정 값 버전을 따로 정의**하겠다는 뜻 → **완전 특수화**
    - 꺾쇠가 비어 있는 건 매개변수를 이미 다 정했다는 의미이고, 정해진 값은 이름 뒤의 `<true>`에 적는다.
    - 특수화의 **원본이 되는 기본 템플릿 선언**이 먼저 있어야 한다.

|상황|결과|
|---|---|
|기본 템플릿 선언 + `template<>` 특수화|✅|
|기본 템플릿 없이 `template<>` 특수화|❌ 에러|
|기본 템플릿만 있고 특수화 없음|문법은 OK, 하지만 어떤 값으로 써도 정의가 없어 객체/`sizeof` 시 에러|

|문법|의미|
|---|---|
|`template<typename T>`|타입을 받는 일반 템플릿|
|`template<bool B>`|bool 값을 받는 일반 템플릿|
|`template<>` + `X<true>`|`true`일 때만 따로 정의 (완전 특수화)|
