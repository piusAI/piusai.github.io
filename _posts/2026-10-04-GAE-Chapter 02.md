#### 2-2 컴파일러, 링커, IDE🌟🌟🌟
##### 1. 소스파일과 전처리
- 소스파일 : 번역단위(Translation Unit : TU)이라고 부르기도 함
- 컴파일러 자체는 헤더파일이 있는지 모르기에 **전처리기(`preprocesser`)** 에 `#include` 구문을 헤더 파일의 내용으로 텍스트 치환해 넘겨준다. 컴파일러는 치환 끝난 결과만 봄!
##### 2. 컴파일과 목적파일
- Translation unit 1개 -[Compile]--> 목적(Object)파일(.obj)에 저장됨
- 목적 파일의 특징
	- 메모리 주소 미결정( TU 내부 기준으로만 정해짐)
	- 다른 TU의 함수/전역 데이터 참조는 비어있음 (unresolved) 
	- 아직 링크되지 않은 상태
##### 3. 라이브러리와 링커

- 정적 라이브러리(Library) : Obj파일 여러 개를 묶은 것. 링크시 필요 부분이 exe안에 복사
- Linker : Obj 파일 + library → 실행 파일(.exe)
- **링커**의 역할:
	- 각 코드/데이터 조각을 배치
	- 전역변수 참조 연결(resolve), **실행 파일 내부 기준의 주소** 결정
	- 주소 : Base주소로부터의 offset(상대값)
	- 모든 기계어 명령어 최종 상대주소 계산
	- 번역 단위(목적파일)에서 확정지 못했던 외부 함수, 전역 데이터 확정
- 메모리 주소값, 외부 참조 확정(resolve)한 상태의 기계어 : exe 파일
 
##### 4. **메모리 주소 확정** 시점

| 단계         | 확정되는 것                              |
| ---------- | ----------------------------------- |
| 컴파일        | 번역 단위 내부 기준 주소                      |
| 링크         | 실행 파일 내부 상대 주소 (Base 주소로부터의 offset) |
| 로드 (실행 직전) | OS 로더가 실제 **절대 주소** 배치              |

- 기계어/ 데이터를 가리키는 주소는 고정된 절대값이 아니라 기준(Base)에 더해질 상대값
- 절대 주소는 OS로더가 프로세스를 메모리에 올릴때 결정된다. 머신/실행 시점마다 달라질 수있기 때문(ASLR 등).
- 링커는 상대 주소까지 결정하고, 절대주소는 로드 시점에 결정
  로컬머신에 따라 로드시 절대주소는 다 다르게 들어간다.

- ASLR - AddressSpace Layout Randomization(주소 공간배치 무작위화)
  프로그램이 실행될 때마다 메모리에 올라가는 주소를 무작위로 바꾸는 OS의 보안기능
##### 5. **DLL**-(Dynamic Link Library,동적 링크 라이브러리)
- (정적) Object - (동적) 실행 파일의 중간 형태  
  호출할 수 있는 함수 담고있음(Library 성격) + OS가 따로 로드한다(Exe 성격) 
- 이미 **링크가 끝난 모듈**이며, 실행 파일과 같은 형식(PE)이지만 단독 실행은 불가.
- 정적 라이브러리와 달리 exe에 복사치않고 **참조만**남김.
- 동적 링크 방식:
	1. 빌드시 : Import Library(.lib)를 통해 이 함수는 이 DLL에 있다"는 정보만 exe에 기록 -> Exe 내부 함수/데이터 주소는 결정되지만, DLL안에 함수에 대한 참조는 미결정( 그래서 "부분적 링크된" 상태)
	2. 실행시 : OS에서 참조 결정되지 않은 함수 찾아 필요한 DLL을 메모리에 로드한후 참조값 갱신(Import Address Table)

- 장점 : DLL만 교체한다면 exe 재빌드 없이 갱신 가능, (단, 함수 시그니처 등. 인터페이스가 바뀌지 않았을떄). 여러 프로그램 공유 가능, 메모리 절약

##### 6. **빌드과정** 요약
```
소스(.cpp)  → [전처리기] #include 치환, 매크로 전개
           → [컴파일러] 번역단위 (TU) 별로 기계어 변환
           → 목적파일(.obj). 주소 미확정, 외부 심볼 미해결
.obj들 +라이브러리 → [링커] → 실행파일(.exe)
```

##### 7. 언리얼에서는?
모듈구조로 빌드하는게 DLL의 개념과 유사
- 모듈 구조 : UE는 코드를 모듈(`Build.cs`로 정의)단위로 나눠서 빌드하고, Editor 빌드에서는 각 모듈이 DLL로 만들어 진다.
- Live Coding : Editor끄지않고 C++수정 사항만 컴파일 해서 실행중인 프로세스에 반영하는 기능, 번경된 부분만 새로 컴파일해 Patch하는 방식이라, 빌드하지 않고 계속 작업 가능.
  => 헤더 구조 변경, `UPROPERTY`추가 등은 Live Coding이 안되는 경우가 많다. 클래스의 Memory Layout이 바뀌면 이미 올라간 객체와 맞지않고, UHT가 생성하는 **Reflection code**도 다시 만들어야 하기 때문이다.

- MSVC : 마소 전용 최적화  
- Clang : LLVM 기반 컴파일러 
- LLVM : 컴파일러 프레임 웤

> 소스코드 → FrontEnd (Clang) →
> LLVM IR → Optimizer → BackEnd  
>   ↓  
> 기계어

| 항목   | MSVC    | Clang + LLVM |
| ---- | ------- | ------------ |
| 구조   | 단일 컴파일러 | 모듈형          |
| IR   | 비공개     | 공개           |
| 최적화  | MS 내부   | LLVM Pass    |
| 확장성  | 낮음      | 매우 높음        |
| 연구/툴 | 제한적     | 풍부           |

- SIMD : Single Instruction Multiple Data
	  하나의 명령어로 여러 개의 데이터를 한 번에 처리하는 병렬 방식의 기법

**로컬 최적화 vs 글로벌 최적화**:  
- 로컬 최적화 : 하나의 Translation Unit(. cpp) 안에서만, 하나의 기본 블록 내에서 만의 최적화  
- 글로벌 최적화: 컴파일러보다 링커가 수행(Translation Unit을 넘나들어야 효과가 있어서)

| 항목    | 로컬 최적화  | 글로벌(LTO) |
| ----- | ------- | -------- |
| 범위    | 함수 / 파일 | 전체 프로그램  |
| 시점    | 컴파일     | 링크       |
| 정보    | 제한적     | 전체       |
| 인라인   | 제한적     | 파일 간 가능  |
| 빌드 속도 | 빠름      | 느림       |
| 성능    | 중간      | 최고       |
- 책의 용어임을 주의

**LTO** (Link-Time Optimization) : 링크 타임에 수행되는 전역 최적화
```
-O0 // 최적화 하지 않은 상태
-O1
-O2 // 속도 최적화
-O3 // 가장 공격적인 수준의 최적화
```

- 개발 디버그 빌드가 inline펼치기와 코드최적화는 당연히 달라야함.

  1. 시간 복잡도
  2. 얼마나 자주불리냐
